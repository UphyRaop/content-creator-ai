# CCAI hosting options and deployment boundary

**Research date:** 19 November 2026  
**Scope:** Read-only production hosting research after Phase 11. This document is research, not a provider selection or authorization to create an account, deploy, change DNS, or spend money. All prices are USD estimates before taxes and may vary by region, usage, egress, and provider changes.

## Current deployment status

The app's public preview uses GitHub Pages. The repository workflow at `.github/workflows/deploy-pages.yml` runs on pushes to `main`, installs dependencies with Node 24, runs `npm run build:static`, and publishes only `dist/`. The static builder writes `dist/index.html`, `dist/timeline-workflow.js`, and `dist/CNAME`. This is a static prototype build; it does **not** run the Next.js server, API routes, SQLite database, or FFmpeg rendering engine. The browser preview is not a production deployment of the backend.

A read-only GitHub Pages API check on 19 November 2026 reported `cname: ccai.ur-project.biz` and `https_enforced: false`; the URL responded over HTTPS, but HTTP-to-HTTPS enforcement was not enabled. To enable it, a repository administrator must open **UphyRaop/content-creator-ai → Settings → Pages → Enforce HTTPS**. If the control is unavailable, follow GitHub's custom-domain troubleshooting guidance and wait until GitHub reports the domain's certificate as ready. No DNS record needs changing for this action. The HTTPS request succeeding is not a separate certificate-chain validation.

Sources: [GitHub Pages HTTPS](https://docs.github.com/en/pages/getting-started-with-github-pages/securing-your-github-pages-site-with-https), [custom-domain troubleshooting](https://docs.github.com/en/pages/configuring-a-custom-domain-for-your-github-pages-site/troubleshooting-custom-domains-and-github-pages).

## Requirements that affect host choice

The production app needs a Node.js runtime for Next.js routes, a writable persistent filesystem for the existing SQLite database and media, and FFmpeg/ffprobe with the required encoders (including libx264 and AAC) for rendering. The repository does not currently define a Docker image or host configuration, so any selected host still needs deployment configuration and a real runtime test for codecs, memory, disk, and cleanup behavior.

The current render queue, job records, and generated render files are held in process memory and temporary directories (`src/lib/ffmpeg-renderer.ts`). A restart can lose job state and temporary exports. A single service instance with its SQLite file mounted on durable storage is the least disruptive initial shape, but it does not make render jobs durable. A separate background worker or multiple replicas would require a durable shared queue and shared media storage (or a redesign to persist job state and artifacts). Fly and Railway volumes are single-machine/single-replica storage; Render disks are attached to one service instance and prevent horizontal scaling of that disk-backed service.

## Decision and operational limits

No provider is selected here. Railway Free and Render Free do not satisfy the production combination of reliable custom-domain service, persistent SQLite, and always-available rendering. Fly.io and a small self-managed VM can fit near the stated USD 5–20 range on paper, but one-machine SQLite limits availability and parallel scaling; video rendering may increase memory use and egress. The app also needs durable render-job state and artifact storage before a separate worker or multiple instances are safe.

Any hosting account, deployment, DNS change, paid plan, or paid API use requires separate owner approval. Before production, verify with a representative render that the selected machine can run the required FFmpeg codecs without memory exhaustion, confirm SQLite backup/restore and persistent mount paths, and define recovery behavior for interrupted jobs. The static GitHub Pages workflow should remain the no-cost prototype deployment unless and until production hosting is separately approved.
